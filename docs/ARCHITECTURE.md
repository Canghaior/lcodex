# 技术栈与代码架构

日期：2026 年 10 月 20 日。状态：P1–P3 当前范围核心条件通过；P4 使用独立捆绑运行时与严格打包清单，已有 0.0.1 Windows 候选。完整安装与用户验收仍按 P4 执行，依据见 validation/P4_PACKAGING.md。

## 技术栈

产品在 `D:\make-codex` 内开发，第一版面向个人本地使用，只接 DeepSeek。

| 技术 | 职责 | 状态 |
| --- | --- | --- |
| TypeScript | 主要语言，编写应用逻辑、界面逻辑、后台与引擎连接 | 用户已确认 |
| React 与 TSX | 编写聊天、项目列表、输入区、文件预览与差异面板 | 用户已确认 |
| CSS | 实现参考截图的颜色、字号、留白、圆角和分栏 | 用户已确认 |
| Electron | 桌面窗口、菜单、应用生命周期及本地进程管理 | 用户已确认 |
| Node.js 能力 | 在 Electron 本地后台中访问必要的系统能力 | 随 Electron 选定版本核对 |
| Codex app-server | 首选执行引擎，作为独立本地进程集成 | P1 验证后决定实际采用版本与配置 |
| DeepSeek API | 模型推理与代码生成服务 | 厂商已确定，具体模型待 P1 |

TypeScript 是带静态类型检查的 JavaScript 扩展，构建后转换为 JavaScript 执行。TSX 是包含界面标记的 TypeScript 源文件形式，不是另一种主要语言。React 和 Electron 是开发工具与运行框架，不是编程语言。

Python 和 Java 都可以实现此类应用。本项目选择 TypeScript，是为了让 React 界面和 Electron 后台使用同一种主要语言，减少界面、通信和后台之间的技术切换。调用 DeepSeek API 不要求使用 Python，也不涉及在本项目内训练模型。

本选型针对自己的产品，不据此推断 Codex 官方桌面软件使用相同实现。

## 分层与进程

```text
React 桌面界面
  项目、聊天、输入框、工具记录、文件与差异
        ↕ 受控的应用接口
Preload 桥接
  只暴露明确允许的操作和事件
        ↕ IPC
Electron 本地后台
  窗口、项目设置、凭据、文件基线、引擎生命周期
        ↕ 引擎连接模块
Codex app-server 本地进程
  模型与工具循环、会话、执行状态、权限执行
        ↕ HTTP Responses
DeepSeek API
```

执行引擎在用户授权项目的隔离副本中修改文件、运行命令和测试；原项目不授予 Agent 写权限。受控后台持有基线与冻结后的审阅版本，在用户点击应用时核对冲突并写回，逐项记录结果。首版不提供一键撤回。引擎与后台能否满足权限、预算、数据和文件保护要求，仍由开发方案 P1 检验；不能以架构图代替控制点的实际能力。

第一版后台运行在用户电脑上，不另设自己的云端应用服务器。模型推理通过 DeepSeek API 完成。

## 各层职责和边界

| 部分 | 负责 | 边界 |
| --- | --- | --- |
| renderer | 呈现对话、项目、工具状态、文件差异，接收用户操作 | 不持有 API Key，不直接运行 shell；界面状态来自实际事件和核对结果 |
| preload | 给界面提供必要的应用方法与事件订阅 | 不暴露任意文件读写、命令执行或完整 IPC 对象；校验消息边界 |
| main | 管理窗口、选择项目、设置与凭据、引擎进程、项目基线和冲突流程 | 后台校验请求与项目范围；耗时文件处理避免阻塞窗口管理 |
| main/engine | 初始化和连接引擎、发送任务、转换事件、关联授权和停止请求、处理断线 | 适配固定版本的接口；不能把发送成功当作执行完成 |
| 执行引擎 | 会话与工具循环、实际任务状态和配置允许的执行能力 | 不在应用内再实现一套互相冲突的 Agent 循环；必要适配由 P1 证据限定 |
| shared | 共用类型、事件与请求约定 | 只定义契约，不在公共模块隐藏文件或模型调用副作用 |

来自模型的 Markdown、代码和工具输出均按内容展示，不能因为出现在界面中就获得 Electron 本机权限。项目内指令不能扩大用户授权。

## 状态与存储

引擎是会话和执行状态的事实来源。应用保存自身项目设置、界面偏好及必要的文件基线；UI 中的执行状态是这些事实的投影，不另行判断模型已完成任务。

引擎运行数据、应用设置、凭据及诊断使用专用的本地数据目录，不能写入产品源代码目录或用户项目后自动纳入 Git。凭据使用系统保护机制；具体存储方案在 P1 核对，第一版不预先引入数据库服务器。

DeepSeek 接入优先采用引擎原有 provider 配置；确需适配时集中在引擎连接或模型适配模块。renderer 不依赖 DeepSeek 的原始响应字段。后续增加模型或更换引擎时尽量保留界面，但不承诺任意引擎可以无成本替换。

P4 的命令适配器只向模型提供命令正文，由后台固定 shell、隔离目录及输出/等待上限，继续通过 app-server 执行，不新增 Agent 循环。Windows 进程管理器在引擎运行前建立 Job 所有权，收尾核对整个进程组；强制回收与任务成功分开，必要时使用没有模型调用和执行入口的新引擎读回持久终态。实现及失败记录见 [P4 稳定性](validation/P4_STABILITY.md)。少量 C# 与 PowerShell 代码仅处理 Windows 文件和进程原生能力，应用主体技术栈不变。

## 计划目录

以下为组织方向，src/main、src/preload、src/renderer、src/shared 和 tests 已建立；尚无必要时不创建空子目录。P2 复用 validation 中经过验证的保护组件，后续提取生产连接，不维护重复的执行循环。

```text
D:\make-codex\
├─ docs\
│  ├─ DEVELOPMENT_PLAN.md
│  ├─ ARCHITECTURE.md
│  ├─ UI_SPEC.md
│  └─ PROGRESS.md
├─ src\
│  ├─ main\
│  │  ├─ engine\          引擎进程、通信、事件处理
│  │  ├─ projects\        项目设置、基线与冲突
│  │  └─ storage\         应用设置与凭据
│  ├─ preload\            受控通信桥接
│  ├─ renderer\
│  │  ├─ layout\          导航栏和分栏布局
│  │  ├─ chat\            消息、工具记录、输入框
│  │  ├─ workspace\       文件预览、差异、命令输出
│  │  └─ settings\        模型和应用设置
│  └─ shared\             数据类型和通信契约
├─ tests\                 必要的行为和集成测试
├─ resources\             产品图标等应用资源
└─ package.json           实施时创建的依赖与命令清单
```

测试项目与独立验收器按开发方案管理。独立验收器不能因位于测试目录就自动获得 Agent 写权限。

## 本地版本保存与 GitHub 同步

初始方案已作为本地 Git 的根提交，分支为 `main`。用户已创建 `https://github.com/Canghaior/lcodex` 并授权同步，也明确允许现有参考截图和提交历史公开；保留已有根提交，不改写历史。

后续开发按可解释的小步提交：完成一个工作包或阶段后执行适用检查，审阅差异、更新执行记录，再提交并推送，核对远程提交；用户选择不设定时任务。确需中断时可建立明确标注未完成的本地提交，不将其写为通过验收。源文件编辑即保存到磁盘，Git 提交额外记录一个可以比较和恢复的版本；只有推送核对成功才记录为已同步。详细规则见 IMPLEMENTATION_PLAN.md。

本地方案版本包含文档及用户提供的界面参考图。密钥、依赖目录、构建产物和运行日志由 `.gitignore` 排除；提交前仍检查实际文件，不能仅依赖忽略规则。
