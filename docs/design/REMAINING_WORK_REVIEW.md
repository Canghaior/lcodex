## 1. 本方案要解决什么

把前次盘点的 34 项待办逐项转成可执行、可验收的设计，同时保留已通过的隔离修改、审阅应用、预算与模型接入。建议保留 TypeScript、React、CSS、Electron 和 Codex app-server；在现有工程内逐步拆分职责，不另造 Agent 执行循环，不在首轮引入云后端或数据库服务。

建议先解决默认安装环境和任务恢复，再补齐项目使用流程，最后对同一候选完成模型、安装与用户验收。多 Agent、插件、跨平台、云同步等另列扩展，不能用这些新增功能替代 P4 的收口。

## 4. 建议采用的关键设计

| 选择 | 建议及理由 |
| --- | --- |
| 引擎和技术栈 | 保留现有已验证组件；先修复已知失败，再逐步提取后台服务 |
| 任务事实 | 引擎历史、进程归属、文件应用日志、费用账本各司其职；UI 文本不能替代事实 |
| 新存储 | 在现有 v2 工作区索引与分聊天文件旁增加版本化小文件；搜索索引可重建，预算和 Key 不参与通用迁移 |
| 流式输出 | 先显示经过过滤的文字预览；完整响应校验通过后才向引擎放行工具，保留现有执行边界 |
| 上下文 | 先做大小预检与明确提示，再验证固定引擎的压缩能力；不可用时提供显式新聊天交接，不伪装无损恢复 |
| 自动重试 | 默认关闭；仅对有证据可安全重试的请求启用有限策略；未知执行与未知费用不能靠重放解决 |
| 项目配置 | 文档发现的命令只作建议；设置冻结到任务，路径限制必须落实到文件工具和 shell |
| 发布验收 | 每个结果绑定源码、模型配置和候选哈希；模拟、真实模型、成品、干净环境分开登记 |

这些选择的替代方案与失败处理见核心架构；尚未验证的引擎接口、系统权限能力必须先做小范围可行性验证，不能直接显示“已支持”。
