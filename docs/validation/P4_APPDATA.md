# P4 默认数据目录故障与修复

2026-10-24；对应 F01/F03/F06/F07/F08/F10。10 月 21 日收到用户“未响应”截图并开始排查，本次继续验证。P4 未整体通过；以下将用户事故、模拟复现和真实本地执行分别记录。

## 用户事故与可复现原因

用户在只读模式询问项目文件数量。首个实际命令为 `Get-ChildItem -Force | Select-Object Mode,Length,Name`。引擎记录显示 Windows 临时目录不可用警告，随后列出 System32，输出约 65 KiB，退出码为 0；Windows 后续记录 Application Hang/AppHangB1。任务没有完整的结束记录，不能把命令退出码 0 当作任务成功。

当前启动宿主下，`%APPDATA%\lcodex` 的实际文件位于宿主包的 `LocalCache\Roaming\lcodex`。普通 `realpathSync` 保留表面路径，`realpathSync.native` 与 Windows 文件句柄查询得到实际位置；目录本身不是 junction。原程序把表面路径交给隔离引擎，导致界面与执行进程访问位置不一致。这是已复现的程序缺陷，不能归因于用户不会操作或模型不会回答。

此次核对时，用户原项目唯一的基线文件哈希仍匹配，应用日志没有向原项目写入的 intent/result。个人账本已有一次请求，估算 0.032283 元；与开发验证账本分开保留，不能撤销已发生的 API 消耗。密钥、聊天、文件基线及遗留锁保持原位，未自动重放任务。

此前成品检查使用 D 盘显式测试配置，默认 Windows AppData 行为覆盖不足。已有 D 盘通过证据保留，不能据此宣称默认目录也已通过。原用户窗口为何停止响应的全部底层机制尚未单独证明；本次修复和验收针对已复现的目录不一致及后续 npm 执行故障。

## 变更

1. 在建立引擎、审阅目录和子进程前，通过原生文件路径解析统一应用数据根目录。仍先拒绝链接与异常存储路径，不迁移或删除既有数据，不放宽项目路径和 Windows 文件保护。
2. 每条实际 PowerShell 命令先检查当前位置是否为本次隔离项目。不匹配时抛出 `LCODEX_PROJECT_CWD_MISMATCH`，正文不执行。原命令、call_id、历史关联和验证命令匹配保持一致；8192 字节总上限包含新增检查。
3. AppData 完整联测另发现 `npm.cmd` 超时。直接 Node、npm-prefix.js、npm-cli.js 和简单 cmd 内置命令可运行；没有扩大沙箱或延长 45 秒命令限额。尝试去掉 npm 启动脚本的全局前缀探测后仍失败，已撤回这项替换。进一步对照显示，简单 Node 脚本由 PowerShell 直接启动可运行，经 `cmd.exe /d /c` 启动也会超时，因此不能把问题仅归因于 npm 的前缀探测。此兼容问题尚未解决，原 npm 分发保持不变。
