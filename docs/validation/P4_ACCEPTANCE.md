## 方法

`tests/packaged-live.mjs --live` 启动真实发布 EXE、真实 app-server/MXC 和捆绑的 Node/npm，通过 DeepSeek 官方 Responses API 完成任务，不模拟模型响应或工具结果。测试器在真实 HTTP 入口外叠加原有开发预算账本，每次请求仍只发送一次；应用个人预算同时工作，开发累计 10 元、每次试验 1 元不因新配置或换阶段重置。

API Key 通过隐藏终端输入及受控 IPC 使用，在测试配置中由 Windows 加密保存，不进入命令行参数、环境变量、报告或仓库。发布包内没有测试注入入口；仅测试器通过 Playwright 的主进程调试能力附加开发预算统计。

每次新建规定初始项目，提前运行外部独立验收器：bug 初始 1/8，小功能初始 1/7。验收器不在模型可写目录内，在只读 MXC 中采集函数结果，协调程序检查断言和完整性；应用前核对原项目不变，应用后再次验收。修复可增加相关回归测试，不能修改无关用户文件或依靠修改项目断言冒充外部验收通过。只读任务需实际读取文件，核对具体代码原因和计算规则，不把静态诊断标为已执行测试。

## 修复与复测要求

产品原先只有第一个工具恰好为配置验证命令时才记录首次退出码。实际工作常常先阅读代码，这会漏掉已经实际执行的失败结果。现改为记录每轮首次匹配配置命令的结果，界面明确显示“首次验证退出码”；这不声称所有更早 shell 操作都未修改文件，任务前独立基线仍由外部验收器记录。

发布程序回归增加“先读取，再验证，再修改并复测”，检查第一次失败不会被后来的成功覆盖。真实 bug 测试允许相关回归测试新增，维持原定的外部 8/8 与无关文件保护标准；首次测试器把文件集合过度限定为单个源码文件，已纠正为与既定任务范围一致。

修复后重新执行三类各三次，结果在实际完成后追加。当前仍未完成 P4 整体验收，也不能用三次小型只读成功推断所有任务的成功率。干净 Windows 和用户对外观、审阅、保留结果的反馈仍另行核对。

首次修复后的运行：只读三次再次通过，分别 3 请求、0.035536 / 0.031998 / 0.031686 元。bug 再次实际复现并修复，但把读取 README 与修改前测试合并为一条工具命令；应用保守地只将完全匹配的独立配置命令识别为验证，因此首次已识别结果为修改后退出码 0。测试器要求该字段必须等于任务前基线 1，导致本轮失败（5 请求、0.063966 元）。原始工具的修改前退出码确为 1，原项目仍未应用。

进一步调整：明确要求模型单独、原样执行配置验证命令；验收器将任务前外部基线、实际前后命令结果及界面首次已识别记录分别核对，不再混为一项。测试中命令文字匹配只用来找执行证据，不授予任何权限；功能正确性继续由外部验收器判定。该调整未将失败轮改写为成功。

截至这次调整，累计 87 请求，占用 1.090582 元（已知估算 0.840582、历史未知 0.25、pending=0）。修复后的安装回归已通过，包含先读取、再测试的首次失败记录；下一轮真实重复任务待执行。

## 真实源码阅读暴露的输入上限

另用当前项目 `src` 目录执行只读检查，要求解释请求、权限、停止与应用的实现。首次运行在七次真实请求后触发 `API_INPUT_SIZE_LIMIT`，未给出最终答案，原源码未变。消耗 0.116860 元、整轮 28.594 秒，保留为失败，不能用九次合成任务成功替代它。

原因是原 48 KiB 上限计算整个发送请求，包括指令、工具定义、历史与工具输出；多个必要源码片段累计后超出。桌面现显式采用 96 KiB，原 P1 的 16/48 KiB 探针窗口保持。每次 0.25 元预留、1024 输出 token、最多八次请求、单试验 1 元和累计 10 元不变；超限在 HTTP 前拒绝，不默默截断上下文。按已复核的峰时输入 2 元/百万 token、输出 8 元/百万 token，以 98304 个输入 token 保守估算约 0.2048 元，仍低于原预留；返回用量继续受 100000 输入 token 及预留金额上限检查。

新增回归证明 70 KiB 请求仅在显式 96 KiB 窗口放行，超出新上限不发 HTTP、不预留费用；模拟返回边界用量时计量仍工作。本机完整回归 88/88，无跳过。第一次在受限工具环境执行时四项链接保护用例无法创建 junction（EPERM）；获准在本机复测后全部通过，没有跳过保护测试。
