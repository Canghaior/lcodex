- 模型侧 `exec_command` 只接受 `cmd`。后台固定实际 PowerShell、当前隔离目录、`login=false`、30000 毫秒等待与 4096 输出 token 上限，再交给原生工具。模型不能提交额外参数扩大范围；命令正文、调用 ID、工具结果和思考历史保留。上下游完整 SSE 均校验，后续调用不合规时整个响应拒绝。
- 项目文件索引来自已有受控快照，最多 80 项、6144 字节，仅包含已准许文件名；不额外扫描或发送整个仓库。索引注明为不可信数据，项目文件仍不能扩权。
- 每轮告诉模型实际剩余请求与已观察到的验证结果。最多仍为八次请求，第八次只用于答复；修改任务配置了验证命令且当前改动尚未通过时，第七次只提供该精确命令，后台同时拒绝其他命令、补丁和多调用。没有配置命令时保持尚未验证，不制造自动通过。
- 工具开始或完成都会使前一次验证失效，只有实际完成、与用户配置完全一致的命令才能重新记录通过。未收到开始事件也不能沿用旧的通过状态。DSML 工具标记冒充最后答复时拒绝，不把文本当命令执行。

## Windows 进程生命周期

原有退出超时本轮再次出现。前两次桌面联测失败，另三次诊断运行中前两次通过、第三次失败；失败时已没有待执行工具，任务处理与出站路由均已报告结束，但进程仍在。固定版本[主收尾实现](https://raw.githubusercontent.com/openai/codex/rust-v0.162.0/codex-rs/app-server/src/lib.rs)还需等待传输及运行时退出；这些观察不能证明上游具体阻塞点已修复。没有用重复运行成功或延长时间代替根因结论。

现在应用通过小型本机进程管理器启动引擎：先以挂起状态创建进程，加入独立的 Windows Job，再开始执行；Job 不允许 breakaway，关闭最后一个句柄会结束所属子孙进程。正常引擎退出后也核对并回收残留助手。管理器监视应用父进程退出；自身崩溃时内核关闭 Job。五分钟管理器兜底只用于失联收尾，不扩大 180 秒任务限额。依据为微软的 [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) 和 [AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject)。

这层只管理本应用启动的进程生命周期，不替代 MXC 文件/网络沙箱，不按名称扫描或结束用户的 Codex、终端或其他进程。管理器与文件保护原生源码一样包含在安装清单中并核对哈希，不修改系统功能。

退出证据分开记录：

| 字段 | 含义 |
| --- | --- |
| `cleanExit` | 引擎自身正常退出且退出码为零 |
| `processesEnded` | 管理器确认本任务 Job 的活动进程数为零，并且管理器正常结束 |
| `reconciledExit` | 非正常退出之后，以全新只读引擎读取持久历史，再次确认预期线程、轮次及终态 |

正常关闭仍等待 25 秒。超时后请求受控回收，不能仅因结束进程就宣布成功。只有原来已确认终态、没有未知或排队工具、全部进程已结束，并且新引擎读回的终态一致，才接受核对后的结果。核对引擎没有模型凭据、模型请求由拒绝入口阻断，也不允许启动轮次或执行命令。失败或中断保持原语义，未知操作仍为需要核对，不自动应用或重放。

明确放弃从未应用的隔离尝试也必须先确认所有进程结束，再独立核对历史；不能把进程已结束当成任务已成功。首次联测发现此入口还在要求旧的正常退出字段，重启后的放弃被拒绝；已按上述证据分离修正，复测结果单独记录。
