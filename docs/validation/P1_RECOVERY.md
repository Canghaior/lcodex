# P1：最近任务文件恢复的可行性

2026 年 10 月 19 日，对应 C5/D02。这里只在自有合成项目观察操作可行性；没有决定首版加入恢复按钮，也没有实现产品恢复 API。

## 普通文件与冲突

此前 [文件保护试验](P1_DATA_AND_PROTECTION.md) 已验证既有文件的持锁版本比对、修改、恢复和冲突拒绝。本次在独立 Git/非 Git 样本补充：

| 场景 | 实际结果 | 边界 |
| --- | --- | --- |
| 撤回任务新建文件 | 独占打开文件，在同一 handle 上比对哈希，再用 Windows SetFileInformationByHandle 设置删除；关闭后文件消失 | 仅固定普通文件，未验证父目录改名/替换竞态 |
| 新文件已被用户改动 | 哈希不匹配，拒绝删除，用户版本保留 | 不采用先查路径再普通删除的做法 |
| 删除过程中用户写入 | 独占锁期间外部写入失败；删除的是已核对的任务版本 | 仅本机固定样本的文件 handle 行为 |
| 恢复已删除文件到空路径 | 私有备份复制为准备文件，File.Move(..., false) 放入原先不存在的路径，内容一致 | 同一卷上的普通文件；跨卷不承诺 |
| 原路径已有用户文件 | 不覆盖的 Move 失败，保留用户版本与准备副本 | 冲突需用户处理 |
| 写入途中进程被结束 | 实际文件只留下部分内容，私有备份仍完整 | 独占锁不能保证写入原子性，当前没有自动崩溃恢复 |

Git 索引哈希保持不变。每个子进程结束后才清理合成副本；故意结束的进程仅为本次明确创建的固定 PowerShell 写进程，无模型和其他用户任务。

实现位于 validation/recovery-feasibility-probe.ts，报告状态使用 observations-confirmed，productRecoveryReady=false。构建和这些实际 Windows 观察通过，不能把“成功观察到半写文件”写成“崩溃恢复通过”。

## 副本容量小样本

另用 64 个固定文本文件、每个 128 KiB，合计 8 MiB 原始内容，分别生成快照和候选副本并逐文件核对 SHA256。额外逻辑字节为 16 MiB，总逻辑内容 24 MiB；本机本次复制加哈希分别 329、333 毫秒。副本当场清理。

这只说明直接复制两份的存储量约为被复制内容的两倍；没有测物理分配、缓存冷启动、大量小文件、依赖目录或真实项目，不能线性推算大型仓库速度。产品须在复制前估算容量、限制并发和保留数量；恢复依据不能因一般缓存清理而丢失。尚未确定产品容量上限。

## D02 的实现成本与决定

普通文本的新增、修改、删除恢复都有可行操作，但完整功能至少还需要：持久的任务/版本/快照记录；崩溃后的“需要核对”与恢复流程；父目录和链接竞态处理；多文件部分完成报告；容量、有效期和安全清理。当前验证代码不能直接用于用户文件。

建议 D02 选择首版后置一键撤回，继续保留基线、审阅和冲突保护；这可以避免把未验证的恢复能力承诺给用户。若用户选择首版纳入，按上述范围补实现和验收，再开放按钮。已提交明确选项，等待用户决定。D01 的写入/应用保护无论选哪项都不能省略。
