## 同项目写任务互斥组件

新增 project-write-lock 仅作为 P1 协调组件：以项目真实路径的哈希定位私有状态文件，用独占创建取得锁，记录随机归属令牌、PID 和时间并刷盘。不同文本路径/目录别名指向同一项目时共用锁；状态目录不接受链接。释放时核对记录，不删除被改写或归属不明的记录。

四项检查通过：同项目排他、不同项目可独立取得锁、目录别名无法绕过、归属变化保留记录，以及真实子进程结束后仍拒绝自动接管。当前完整回归 51/51。异常退出不会仅凭“PID 不存在”就清除锁，须先核对遗留操作。

这协调的是遵守协议的本应用实例，不能阻止用户编辑器或任意 shell 写文件，不替代 C4 的文件版本/应用保护。组件还未接入桌面任务入口，也没有把自动清除过期锁作为已实现功能；锁记录未来必须放在 Agent 不可写且清理规则排除的位置。

## 隔离候选与单文件恢复试验

新增 file-protection-probe.ts，在 Git 脏工作区和非 Git 样本分别执行：

1. 在外部候选目录修改副本，核对原项目哈希完全不变。
2. 原项目已经出现用户修改时，持独占文件句柄重新读取并校验哈希；版本不符，拒绝应用，保留用户版本。
3. 正常应用期间持 Windows FileShare.None 句柄，模拟的外部写入被操作系统拒绝；完成后文件内容正确。
4. 最近任务的修改文件仍匹配任务结果时，使用相同锁与版本检查恢复原内容。
5. 后续又有用户改动时，拒绝恢复；Git 索引、既有用户笔记和独立验收器保持原样。

以上两种样本均通过。试验是受信任协调程序持锁，不把受信任权限开放给模型命令，也不是新增产品的完整写入接口。它证明普通小文件上可以缩小“检查后再写”的竞态；尚未处理创建/删除恢复、链接与路径替换、崩溃恢复、多文件一致性。写入途中进程崩溃仍可能留下部分内容，必须保留基线和待核对记录，不能宣称已有原子事务。

本样本原文件 104 字节、候选 124 字节，只足以验证行为，不足以制定真实项目的复制速度或容量阈值。实际副本、快照、依赖处理及清理必须继续量化。

| 选项 | 用户体验 | 实现影响 |
| --- | --- | --- |
| A 直接写原项目 | 授权后改动立即落盘，审阅的是已发生改动 | 当前任意 shell 写入无法保护并发用户编辑；需要限制写命令或增加统一受控写入层。不能靠“请用户别编辑”满足已有保护要求，工作量较高且实现路线仍有风险 |
